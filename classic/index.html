Complexity analysis rules

  • Sequential code는 더하고 (O(a) + O(b)), nested loop는 곱함 (O(a · b)). 마지막엔 dominant term만 남기고 constant factor는 버림 → O(n² + 3n) = O(n²)
  • loop 안의 x in list, list.pop(0), s += c, slicing은 각각 hidden O(n). loop와 곱해져서 전체가 O(n²)이 됨
  • 매 step마다 input이 절반으로 줄면 O(log n) (binary search, heap, balanced tree)
  • Recursion = number of calls × work per call. branching factor b, depth d → O(bd)
  • Memoization DP = number of states × transition cost per state
  • comparison sort를 한 번이라도 하면 최소 O(n log n)
  • Amortized O(1): list.append는 가끔 resize로 O(n)이지만, n번 하면 총 O(n)이라 한 번당 O(1)
  • Hash operation (dict / set): average O(1), worst O(n) (collision)
  • Space complexity: input은 빼고 추가로 쓰는 memory만 셈. recursion의 call stack depth도 포함 → tree DFS = O(h)
  • 새 object를 만들어 return하는 operation(slice, sorted(), a + b)은 그 크기만큼 space를 씀
  • Graph: adjacency list로 BFS / DFS = O(V+E) time, O(V) space

Python data structures: syntax + Time / Space complexity

data structure:
variable names: a=list · d=dict · st=set · q=deque · h=heap · s=str

T = time complexity, S = space complexity (input을 뺀 extra space). * = amortized. dict / set은 average case (hash collision이 몰리면 worst O(n)). — = 지원하지 않거나 의미 없는 operation.

📘 Amortized simulator: list.append는 왜 O(1)인가

list는 memory 칸(capacity)을 넉넉히 잡아둠. 빈칸이 있으면 넣기만 함(cost 1). 꽉 차면 더 큰 공간을 새로 잡고 기존 element n개를 전부 copy(cost n+1). 버튼을 눌러보면서 average cost가 어떻게 되는지 확인.

growth factor:
append마다 든 cost (최근 80번). 높은 막대 = resize copy

왜 average cost가 constant가 되나 (2× 기준)

resize는 size가 1, 2, 4, 8, … n일 때만 일어남. copy cost 합 = 1 + 2 + 4 + … + n < 2n. 여기에 append 자체 cost n을 더해도 total 3n 미만 → 한 번당 average 3 이하 = O(1). growth factor가 1.125×여도 constant만 커지고 O(1)은 그대로. 반대로 매번 +1칸씩 늘리면 copy 합이 1+2+…+n = O(n²)이라 average O(n)이 됨. 그래서 capacity는 곱으로 늘려야 함.
pop()은 끝 칸만 비우면 돼서 O(1). 많이 비면 공간을 줄이는 resize가 가끔 있어서 이것도 엄밀히는 amortized O(1). space는 둘 다 O(1)*.

📘 pop() vs pop(0): 어떤 element가 움직이나

a = [3, 1, 2]

a.pop()         [3][1][2]  →  [3][1][ ]         움직이는 element 0개         → O(1)

a.pop(0)        [3][1][2]  →  [ ][1][2]
                           →  [1][2][ ]         ← ← 뒤의 n-1개가 한 칸씩 shift → O(n)

a.insert(0, 9)  [3][1][2][ ] → [ ][3][1][2]
                             → [9][3][1][2]     → → n개가 한 칸씩 shift      → O(n)

q.popleft()     deque [3][1][2]  →  [1][2]      시작 pointer만 옮김           → O(1)

list는 contiguous array라서 중간에 빈칸을 둘 수 없음. 그래서 앞쪽을 건드리면 뒤의 element가 전부 shift됨. deque는 block을 연결한 구조라 양 끝 모두 다른 element가 안 움직임.

📘 Hash table: dict / set이 O(1)인 이유

key → hash(key) → % slot 수 = 저장 위치. lookup할 때도 같은 계산으로 바로 그 slot에 감. key를 바꿔 넣어 보기 (쉼표로 구분). 설명용으로 단순화한 hash function이라 실제 Python hash 값과는 다름.

포인트

같은 slot에 여러 key가 오면 collision. 그 slot에서 key를 하나씩 comparison 해야 함. slot 수를 1로 바꿔 보면 전부 한 slot에 몰려서 사실상 list처럼 O(n)이 됨. 이게 worst case. 실제 dict는 약 2/3가 차면 slot 수를 늘려 다시 배치(resize)해서 slot당 key 수를 낮게 유지함 → average O(1). CPython은 이 그림처럼 slot에 list를 매다는 chaining이 아니라 빈 slot을 찾아가는 open addressing을 쓰지만, complexity를 이해하는 데는 차이가 없음.

📘 Heap visualizer: list가 tree로 보이는 방법

index i의 child는 2i+1, 2i+2. parent는 (i-1)//2. 규칙은 "parent ≤ child" 하나. push / pop 해보면서 swap이 tree height(log n)만큼만 일어나는 걸 확인.
